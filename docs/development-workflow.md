# 開発ワークフロー

開発者・開発エージェント向けの必須ルール。MyKanban の既存ワークフローに従い、本資料は Pomme Compose 固有のタスク粒度・実装・PR・レビュー要件を定める。MyKanban 自体のステータス、オーケストレーション、マージ方式等を独自に再定義しない。

## 1. 開発単位

- 原則 1 コンポーネント 1 Issue・1 ファイル・1 PR。複数コンポーネントを一括で実装する PR を作らない。
- コンポーネント固有の型、Scope、内部実装、Compose Preview はコンポーネントと同じ Kotlin ファイルに配置する。
- テスト、サンプル、複数コンポーネントに共通する基盤・型・処理は責務に応じて別ファイルに配置する。複数のコンポーネントを同じファイルにまとめない。単一コンポーネントの実装を目的なく分割しない。
- プロジェクト基盤、テーマ共通基盤、複数コンポーネントの共有描画基盤、統合検証等は独立した Issue / PR とする。例外の理由と変更範囲を Issue に明記する。
- 依存関係は GitHub Issue の Blocked by で管理する。依存の未解決を局所的な代替実装や重複定義で回避しない。

## 2. タスク設計

MyKanban の既存 Issue テンプレートを尊重し、その項目内に次の情報を含める。

| 必須情報 | 内容 |
| --- | --- |
| 概要 | 対象コンポーネントと目的 |
| 参照 | 対応 SwiftUI 公式 API、対象 iOS、必要な外観・挙動の根拠 |
| 設計方針 | 責務、全体設計との関係、共有基盤との境界 |
| IF 仕様 | 公開関数・型・引数・既定値・Scope・Style 等 |
| 挙動仕様 | 状態、操作、Style、配置文脈、例外時の挙動 |
| 利用イメージ | Kotlin の呼び出しコード |
| Preview 仕様 | 全 Style、Light / Dark、必要な状態・文脈 |
| テスト仕様 | 検証内容と完了条件 |
| 対象外 | 今回実装しない機能 |

公開 IF と具体的な挙動は着手前に設計し合意する。実装担当は独断で未承認の IF や仕様を追加・変更・簡略化しない。不足や技術的な問題は阻害事項として明示し、必要な設計合意を得る。

## 3. MyKanban の責務分担

1. 設計担当：要件、IF、挙動、Preview、テスト、依存関係を明確にして Issue を作成し、既存ワークフローに従って登録する。
2. 実装担当：割り当てられた Issue のコード、Preview、テスト、検証を実施し、Preview 画像付き PR の作成まで責任を持つ。
3. レビュー担当：Issue と PR の整合性、SwiftUI 準拠、公開 IF、実装品質、全 Preview の画像・網羅性、必要な検証結果を確認する。
4. マージ・完了：CI とレビュー等の既存 MyKanban の条件を満たしてから処理する。画像未添付や描画未確認を完了として扱わない。

基盤 → PommeColorScheme → PommeTheme を先に整え、依存が解消したコンポーネントから並行開発する。Form / List / Section の共有描画基盤は先に設計し、必要な依存を Issue に明示する。順序の詳細は個別の依存関係によって決める。

## 4. Compose Preview と PR 画像（必須）

### Preview の定義

- 全 UI コンポーネントに、実装する Style ごとの独立した Preview 関数をコンポーネントと同じファイルに定義する。Style のないものも Preview 必須。
- 各 Preview は Light / Dark 両テーマを描画可能にする。共通の multipreview annotation 等を利用してよい。
- 通常・無効・選択・入力状態、テキスト・アイコン、長文等の必要な状態は Issue に定め、同一 Style の Preview 内で比較可能にしてよい。
- Automatic 等、Form / Toolbar / 通常画面で外観が異なる場合は、必要な文脈それぞれで Light / Dark を確認する。
- 本番コンポーネントとテーマを使う。サンプル画面、モック、Preview 専用の外観実装で代用しない。
- Style の追加・変更時には同じ PR で Preview を追加・更新する。

### PR 本文の画像

**UI コンポーネントの実装・変更 PR には、各 Style の Light / Dark 両方の実際の Compose Preview の画像を必ず貼る。** Style のないコンポーネントも同様に Light / Dark 両方を添付する。

- 画像は当該 PR のコードを実際にレンダリングしたものとする。画像が閲覧できる状態で PR 本文に埋め込み、Style・テーマ・必要な文脈が識別できるようにする。
- 画像の枚数は Style × 2 テーマを最低限の確認単位とする。主要状態を一枚にまとめてもよいが、全 Style・両テーマ・必要な文脈が省略されないこと。Automatic の外観が文脈により異なる場合はその文脈の画像も両テーマ分必要。
- PR 更新で見た目が変更された場合は、画像も当該実装に合わせて更新する。
- 例：PommeButton の Style が Automatic、Plain、Borderless、Bordered、BorderedProminent、Glass の6種類なら、最低12件の Style × テーマの画像確認単位が必要。Automatic の追加文脈分は別途添付する。これは例であり Style の採用範囲を確定するものではない。
- 画像の作成・添付手段がない場合は阻害事項として報告する。画像なしの PR を実装完了・レビュー通過・マージ可能とは扱わない。ビルド成功、テスト成功、モック画像、画像へのリンクだけでは代替不可。

PR 本文の記載例（既存テンプレートの該当欄を利用する）：

```markdown
## Preview

| Style / Context | Light | Dark |
| --- | --- | --- |
| Glass | ![Glass Light](実画像URL) | ![Glass Dark](実画像URL) |
| Automatic / Toolbar | ![Toolbar Light](実画像URL) | ![Toolbar Dark](実画像URL) |
```

画像のレンダリング・アップロード方法は基盤設計時に確定する。画像の添付義務は方法の確定を待たず要件とする。

## 5. 実装品質・レビュー

- 公開 API を最小化し、不要な型・関数は internal / private とする。公開 API には KDoc で責務、引数、既定挙動を記載する。
- Compose 標準機能を優先し、不要な独自実装、共通処理の局所実装、未承認の外部依存を追加しない。
- 非 UI ロジックの行カバレッジは 90% 以上を目標とする。変更に応じた UI テストとユニットテストを用意する。Preview はテストの代替ではない。
- 安定版リリース後の破壊的変更は原則禁止。ビルド、Lint、テストの CI 成功をマージ条件とする。具体的な CI 設定は基盤設計で決める。
- SwiftUI の名称・責務・既定挙動・Style の文脈適用を照合する。利用者に不要なラッパー・余分な手動装飾や独自操作を要求しない。
- Issue の変更範囲、共通基盤との責務分離、公開範囲、全 Style の Preview と実画像、Light / Dark の両方、必要な状態・文脈、最新の PR 実装との一致をレビューする。
- 詳細な実装・完了チェックは [.agents/skills/development/SKILL.md](../.agents/skills/development/SKILL.md) に従う。
